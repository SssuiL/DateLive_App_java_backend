# 漫聊后端 Java 全量重构实施方案

日期：2026-09-15

## 1. 已确认的决策

- 客户与团队已确定用 Java 重构全部后端。
- 项目尚未上线，没有交期压力，不要求保持旧服务运行。
- 独立重建、完整验收后一次切换；不为线上渐进迁移建立双写、长期双后端或按模块切流机制。
- 最终在线业务、WebSocket 网关、媒体任务编排、后台调度和必要运维功能不依赖 Python 服务。
- 旧实现用于提取业务规则与回归样例，不按文件逐行翻译；已识别的全表扫描、同步阻塞、无界等待等问题不予复制。
- 保留现有工作成果与数据，任何测试只使用隔离数据库、缓存命名空间和存储前缀。重构授权不等于删除数据。

### 已发现的特殊事项

- 登录密码当前采用 PBKDF2-HMAC-SHA256，120000 次迭代，自定义存储格式。若导入测试账号，需要验证 Java 按相同盐编码和格式校验；新密码策略另行设计，不通过降低成本参数提速。
- JWT 使用 HS256，并包含会话状态相关逻辑。接口返回 token 不代表认证闭环完成，还需刷新、撤销、封禁、设备会话和 WebSocket 鉴权。
- 直播 provider 注册表目前仅有 MockLiveProvider，生产 provider 列表为空。必须区分已有模拟能力与真实接入，不能以 mock 用例冒充真实供应商验收。
- 现有支付代码包含微信支付适配；其配置、供应商账户和真实回调联调情况尚未验证。
- 注册体验问题包含客户端串行请求、反复新建 HTTP 连接及推送注册等待；Java 重构时同时测客户端端到端耗时。
- 前一轮已单独修改 Flutter，使注册不等待推送注册，认证相关 13 项测试通过；尚未打包交付。该变更独立于后端重构进度。

## 3. 技术与工程结构

技术基线拟定为 Java 25 LTS、Spring Boot 4.1.1、Maven Wrapper、Spring MVC、Spring Security、Bean Validation、Spring JDBC、PostgreSQL、Redis、Flyway、Micrometer/Actuator，以及由 Spring Boot 管理的测试依赖与 Testcontainers。

Java 25 为 LTS，Spring Boot 当前官方系统要求允许 Java 25。具体 JDK 发行版、依赖补丁版本和容器镜像在 M0 构建验证后锁定，不在构建中使用浮动 latest。关键供应商 SDK 必须先验证兼容性。

使用一个代码仓库，业务服务采用模块化单体。模块不等于独立微服务；账号、交易等核心事务先在同一业务应用内完成。

| 构建/运行单元 | 职责 |
| --- | --- |
| core-api | 业务 API、认证、权限、交易、后台管理 |
| realtime-gateway | WebSocket、在线状态、事件广播、背压和连接治理 |
| job-worker | 媒体任务、扫描、审核编排、事件重试和周期调度 |
| ops-tools | 初始化、数据校验、迁移、修复、备份恢复验证等必要命令 |

可复用业务模块和协议在仓库内共享，先确定依赖边界，再决定 Maven 子模块粒度。数据库访问以显式 SQL 为起点，清楚表达索引利用、行锁和事务；不引入全库扫描式实体转换，也不一开始全面使用响应式框架。

图片处理使用 Java 库；音视频处理继续调用 FFmpeg/ffprobe；扫描可以使用 ClamAV 或外部服务。它们是外部处理工具，不要求把编解码器和扫描引擎重新实现成 Java。人像检测采用 Java 可用绑定或推理服务供应商，必须对比现有样本效果。

虚拟线程如启用，仅用于合适的阻塞 I/O，并同时设置数据库与外部服务并发预算；不把虚拟线程等同于无限处理能力。

初期保留 PostgreSQL、Redis 和已有对象存储协议。Kafka、Kubernetes、服务网格不作为重构前置条件；先以测得的容量和部署需求决定是否增加基础设施。

## 4. 模块范围与实施顺序

### M0：可构建工程与契约、数据基线

- 建立 Java 工程、可复现构建、CI、日志、请求编号、指标与隔离测试环境。
- 导出运行时 OpenAPI 与 WebSocket 事件合同，整理管理权限、业务状态机、错误码和参数校验。
- 从 PostgreSQL 实际迁移结果核对表、字段、约束、索引，建立新项目 Flyway 初始基线。
- Alembic 历史保留作参考，不机械复制为 74 个 Java 迁移。新库从 Flyway 基线初始化。
- 生成脱敏测试数据集，识别需保留的账号、内容和媒体。旧数据如需导入，执行单独导入与校验流程。
- 先做注册链路基线：创建账号、获取用户资料、推送设备、网络建连分别计时。

完成标准：干净环境可构建启动；PostgreSQL/Redis 集成测试可运行；接口和数据清单可追踪；没有连接现有数据库执行自动改表。

### M1：账号与认证完整闭环

- 注册、短信验证、密码/短信登录、密码重置、刷新 token、退出登录、设备会话。
- 用户资料、封禁状态、认证审计、推送设备注册及管理端鉴权基础。
- 原始密码不进入日志；验证码重放和并发消费、令牌轮换与撤销有测试。
- 需要保留旧账号时，用固定跨语言测试向量验证密码与 token 兼容性。
- Flutter 对接注册到登录态恢复全链路，推送设备操作不阻塞注册成功。

完成标准：真实 Java API + PostgreSQL 联调通过；旧约定和新实现差异有记录；注册体验有端到端采样结果；模拟短信和真实短信验收分开标记。

### M2：媒体与普通业务

- 上传、对象存储、私密访问、签名 URL、衍生文件、隔离扫描和审核、失败重试、删除任务。
- 用户资料媒体、动态、评论、点赞、Emoji 点评、探索匹配、好友与群组治理。
- 通知中心、推送偏好、客服工单、客户端版本检查、管理后台相应能力。
- 推荐规则按现有业务实现，未来新增算法需求单独管理。

完成标准：媒体访问权限和删除链路完整；查询分页、索引和列表接口没有已知逐条数据库查询放大问题；处理失败可恢复。

### M3：完整资金领域

- 钱包、金币账户、账本、充值订单、支付回调、礼物扣费、退款、通话计费、主播收益及结算。
- 明确一次事务内的余额更新、账本、业务记录、Outbox 事件。
- 整数最小单位或明确精度的十进制处理金额，不使用浮点数。
- 验证幂等键与参数冲突、重复/乱序回调、并发扣款、失败回滚、余额与分录一致性。
- 资金写操作集中在交易模块，其他业务模块调用明确的领域接口。

完成标准：PostgreSQL 并发测试、对账和故障注入通过；支付 SDK mock 测试与供应商环境联调分开验收。

### M4：直播与实时消息

- 开播准入、实名审核、设备预检、房间状态机、流凭证、服务商回调、断流恢复。
- 连麦、预约提醒、关注通知、房管、禁言、踢人、举报、申诉、内容治理。
- 聊天历史、发送去重、引用/撤回、已读、未读计数、离线推送与可靠投递。
- 三类 WebSocket 协议、Redis 事件语义、多网关扇出、重连、慢连接背压、热点房间限流。
- Java 网关使用与 API 一致的会话撤销和权限规则，不维持另一套独立认证事实。
- 真实直播/RTC 供应商接入需实际 SDK、账号和回调环境；缺少时明确标为待接入，不声称全功能完成。

完成标准：双客户端端到端场景、多实例广播与故障恢复通过；事务 Outbox 和网络投递指标可分别观察；直播业务与音视频质量分别验收。

### M5：全量验收与一次切换

- 账户注销清理、存储删除、审计、运营数据、后台任务、必要运维命令补齐。
- API/事件兼容性、所有业务领域、权限、安全和并发测试完成；逐项关闭接口清单。
- 在接近目标服务器的配置上完成冷/热请求、独立压测机、长时间运行和故障恢复测试。
- 完成全新部署、数据导入、备份恢复、密钥配置、日志脱敏、告警、操作文档。
- 生成联调环境与新版 Flutter 测试包，客户验收后整体切换到 Java。
- 归档旧 Python 仓库和迁移证据，移除最终部署中所有 Python 服务/Worker；数据不因归档自动删除。

## 5. 接口和数据库原则

- Flutter 现有路径、字段、错误码、分页、时间格式和消息事件尽量保持兼容。
- 如果现有契约需要改进，先记录差异并同步修改 Flutter 与测试，不维护隐藏的不兼容行为。
- 初始化数据库使用单一工具 Flyway，不使用 ORM 自动 update/create 修改现有库。
- 新结构可以调整，不为未上线系统强行保留所有历史冗余字段。调整须有数据映射、业务验证和导入策略。
- 旧数据导入在隔离库验证数量、外键、余额/分录、媒体引用和账号可登录性。
- 一次切换不需要线上双写，但仍需要可重复部署、数据备份和可恢复的切换步骤。

## 6. 性能验收方法

先约定服务器资源、数据规模、并发模型和业务流量，再给出容量承诺。历史本机 500 连接测试不是生产容量承诺。

首个里程碑暂定工程目标：测试环境热状态下，注册 API 在明确的低并发负载下 P95 不超过 500ms；手机注册到可用登录态在规定网络条件下 P95 不超过 2s。均为待验证目标，不是已实现结果。密码安全参数不为满足目标而降低。

记录 P50/P95/P99、错误率、超时/429 比例、CPU/RSS、数据库连接等待、事务/锁等待、外部调用、Outbox 积压、WebSocket 投递延迟。冷连接、TLS/DNS 和移动网络单独采样，不把健康接口耗时当成注册性能。

同样的资源、数据与请求模型比较旧后端和 Java，发布吞吐与延迟报告。数据库、媒体与实时网关的瓶颈分别处理。

## 7. 完成的定义

- 业务完整：全部接口和后台任务有实现或有明确审核过的替代/移除记录。
- 数据正确：资金、会话、媒体权限、状态机、删除清理有集成和并发验证。
- 客户端可用：Flutter 主路径和失败路径完成联调。
- 外部服务真实：模拟适配器与真实供应商接入状态清晰，不能混用完成口径。
- 性能有证据：端到端结果符合约定负载与目标，资源配置可复现。
- 可运维：部署、日志、指标、配置、备份恢复和故障处理可执行。
- Java 全量接管：正式部署没有必须依赖的 Python 在线进程和定时任务。

不以生成了多少文件、工程能启动或接口返回 200 作为完成依据。进度按可验收业务闭环汇报，不在盘点前承诺固定工期。
